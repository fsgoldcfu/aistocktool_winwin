# 交易日誌與策略驗證模組

**作者：Manus AI**  
**功能：把短炒推介轉成可驗證的紙上或實盤交易紀錄。**

> 交易日誌只記錄使用者自行決定並手動輸入的交易結果。它不會自動落單，不會保證盈利，亦不會把策略分數當成勝率。

## 1. 模組做甚麼

每次美股或港股短炒掃描後，你可由頁面底部的「交易日誌與實際成效」選擇一個訊號，建立**紙上交易**或**實盤交易**計劃。系統會保存當刻的入場、目標、止蝕、股數、Tradeability Score、催化狀態及推介原因快照。

交易結束後，你手動填寫實際出場價、富途買入／賣出的實際費用，以及美股的美元兌港元換算率。系統才會計算成本後淨損益和 R 倍數；它不會以目標價或預估費用假裝成實際業績。

| 指標 | 計算方法 | 意義 |
|---|---|---|
| 成本後淨損益 | 實際價格損益（換算 HKD）－實際買入費用－實際賣出費用 | 真實交易經驗的基本結果 |
| R 倍數 | 成本後淨損益 ÷ 原計劃風險金額 | 可跨股票價格和倉位比較的結果 |
| 成本後勝率 | 成本後淨損益 > 0 的完成交易 ÷ 所有完成交易 | 只能在樣本足夠後理解 |
| 每筆期望值 | 所有完成交易的成本後淨損益平均值 | 比單看勝率更有用 |
| 最大回撤 | 完成交易的累積損益由高位回落的最大金額 | 衡量連續壞情況下的風險 |

## 2. 必須先在 Supabase 建立資料表

在 Supabase Dashboard 開啟目標 project，前往 **SQL Editor**，新增 query，貼入並執行：

```text
supabase/migrations/20260815040000_create_trade_journal.sql
```

請使用更新包內該 SQL 檔的**完整內容**。此 migration 會建立 `trade_journal_entries`、啟用 Row Level Security，並限制每位登入使用者只能讀取、建立、更新和刪除自己的日誌。沒有完成這一步，前端會顯示無法讀取或建立交易日誌。

## 3. 更新檔案次序

請在同一個 Git commit 一次過更新下列檔案。不要混合舊 ZIP 或逐檔 deploy。

1. `supabase/migrations/20260815040000_create_trade_journal.sql`
2. `lib/tradeJournalMath.ts`
3. `components/TradeJournalPanel.tsx`
4. `app/dashboard/page.tsx`
5. `app/page.tsx`
6. `scripts/verify-trade-journal.ts`
7. `package.json` 與 `package-lock.json`

之後在 Codespaces 的 project root 執行：

```bash
npm ci
npm run typecheck
npm run verify:trade-journal
npm run build
```

## 4. 正確使用流程

第一，掃描後先選一個你真正想追蹤的訊號，建立**紙上交易**。即使你未有下單，這也會留存當時的技術、催化和成本後盈利條件。

第二，如果實際成交，選擇**實盤交易**，並在出場後由富途成交記錄抄入實際出場價、買入／賣出費用。美股須加入實際或採用的 USD/HKD 匯率；港股匯率固定為 1。

第三，累積足夠完成交易後，才可按市場、美／港股、催化狀態、Tradeability Score 區間、退出原因及市場環境分組分析。建議先以紙上交易累積足夠樣本，然後再以實盤小倉位驗證；不要由少量成功交易推斷策略已經有效。

## 5. 目前限制和下一步

目前介面顯示全體完成交易的基本指標，不會在樣本太小時宣稱有統計優勢。下一步應在累積足夠交易後，加入交易日匯出、以週期切分的 walk-forward 報表，以及按 setup／催化類型／持倉時段的樣本外比較。所有分析都必須包含實際費用、滑點、未成交和跳空情境。
